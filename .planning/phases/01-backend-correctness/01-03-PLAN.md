<objective>
Fix the two remaining route-handler defects, both concentrated in `routes.py` and sequenced last because Plans 01 (connection call sites) and 02 (slowapi removal in routes.py) touch the same file first:

1. BUGFIX-03 (idempotency replay): The current replay path returns a hardcoded `accepted_segments=0, rejected_segments=0` (routes.py lines 93-99) instead of the original response — a broken idempotency guarantee that causes clients to believe their submission failed and retry indefinitely. Fix by adding a `response_body TEXT` column to `idempotency_keys` (via a guarded `ALTER TABLE` in `init_db()`, D-06), storing the serialized JSON response at write time (D-07), and replaying it byte-for-byte (D-08). Legacy `response_body IS NULL` rows are treated as a cache miss and reprocessed fresh (D-09) — never the old zero-count response.
2. API-05 (deprecation header): The deprecation warning for `timestamp_utc` is currently only logged server-side (routes.py lines 220-227 in POST; line ~314 in GET). Deliver it to clients via an `X-Deprecation-Warning` HTTP header on BOTH POST /v1/ride_summary and GET /v1/eta (D-10), attached by returning `JSONResponse(content=model.model_dump(), headers={...})` after constructing the Pydantic model for validation (D-11, D-12). Because this introduces a NEW client-visible API contract, `docs/api.md` (the canonical spec) MUST document the header FIRST, before any test or implementation, per CLAUDE.md Global Workflow Rule 1 (Spec-First Development) and Rule 2 (Spec → Tests → Code order).

Also fix, as an explicit drive-by, the 2 pre-existing `test_idempotency.py` failures caused by the stale 2-arg `store_idempotency_key()` call signature — thematically adjacent to BUGFIX-03 and touched here anyway (per RESEARCH.md Open Question 1). The other 6 baseline failures remain out of scope (Phase 6 territory).

Purpose: Restore the idempotency contract and deliver the deprecation signal clients need — the last two P0/correctness items of the phase.
Output: `docs/api.md` spec update (X-Deprecation-Warning header, spec-first), `schema.sql` + `db.py` ALTER guard, `idempotency.py` response_body read/write, `routes.py` replay + deprecation-header returns, new deprecation-header test, and the 2-test drive-by fix.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API (Idempotency-Key) | The `Idempotency-Key` header and request body are attacker-influenceable; replay must return the original response only for a matching body |
| client→API (deprecated field) | `timestamp_utc` is a legacy client-supplied input; its use must be signaled back to the client, not just logged |
| API→SQLite | The cached `response_body` is read back and deserialized; NULL legacy values must not crash the handler |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-Replay | Denial of Service (indirect) | `routes.py` idempotency replay + `idempotency.py` | high | mitigate | Return the original stored response (`response_body`) on replay instead of stale zeros (BUGFIX-03, D-06..D-08) — removes the client incentive to retry indefinitely believing the submission failed, which otherwise amplifies load |
| T-03-NullCrash | Denial of Service | `routes.py` replay deserialization | medium | mitigate | Explicit `if response_body is not None:` guard before `json.loads` so legacy NULL rows fall through to fresh processing rather than raising (D-09, RESEARCH.md Pitfall 2) |
| T-03-Tamper | Tampering | idempotency body-hash verification | low | accept | Existing SHA256 body-hash 409-on-mismatch logic is untouched by this plan — replay only returns the cached body when the hash matches or was not verifiable (pre-existing H1 control) |
| T-03-SC | Tampering | pip dependency set | low | accept | This plan installs no new packages (stdlib `json` only); no supply-chain surface added. |
</threat_model>

<objective>
Add `GET /v1/routes/{route_id}` (API-02): returns route metadata (full `RouteResponse` field set) plus a `directions` array, each direction holding its ordered stop list. Stops-only — NO trip-level or schedule data (D-01, narrowing REQUIREMENTS.md's broader "stops, trips, schedules" wording to ROADMAP's literal "ordered list of stops").

Locked decisions: D-01 (route metadata + stops-only directions), D-02 (`directions: [{direction_id, stops}]` array shape), D-03 (stop entry fields), D-04 (most-common-shape representative trip picks the ordered stop list for branch variants), D-05 (zero-trip route → 200 + `directions: []`, never 404), D-06 (`HTTPException(404, detail={...})` style).

**D-23 (planner-resolved micro-decision):** RESEARCH.md Open Question #1 — when one direction has trips and the other has zero trips (partial service), the zero-trip direction is OMITTED from the `directions` array entirely (it does not appear with `stops: []`). This is symmetric with D-05's philosophy of "don't manufacture structure for data that doesn't exist." Locked here so the code choice is traceable, not implicit.

Purpose: Mobile clients can render a route's stop sequence (per direction) in one call.
Output: 1 new route handler, 3 new Pydantic models, 4 new integration tests, 1 new conftest fixture, 1 new docs/api.md section.

CLAUDE.md order: Task 1 spec, Task 2 RED tests + fixture, Task 3 GREEN implementation.
</objective>

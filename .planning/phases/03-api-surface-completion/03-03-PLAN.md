<objective>
Extend `GET /v1/stops` with geospatial radius search (API-03): new `lat`, `lon`, `radius_m` query params returning all stops within `radius_m` meters of `(lat, lon)`. Additive to the existing endpoint (D-12), not a new endpoint.

Implementation: a Python equirectangular `bounding_box()` computes a lat/lon range used as a cheap SQL `BETWEEN` pre-filter, then a pure-Python `haversine_m()` second pass removes bounding-box-corner false positives — no spatial index, no new dependency (RESEARCH.md Pattern 1). Locked decisions: D-13 (bbox + radius mutually exclusive → 400), D-14 (lat/lon/radius_m all-or-nothing → 400), D-15 (radius_m cap 2000 → 400), D-16 (lat/lon range-validated → 400), D-17 (drive-by: apply the same range validation to the existing `bbox` coordinates, which today lack it despite the docs claiming otherwise).

CRITICAL correctness constraint (RESEARCH.md Pitfall 1): lat/lon/radius_m MUST be declared as unconstrained `Optional` `Query(None)` and validated MANUALLY in the handler body returning `JSONResponse(400, {"error": "invalid_request", ...})`. FastAPI declarative `Query(ge=/le=)` bounds produce a 422 in FastAPI's own error shape, violating D-15/D-16's required 400 envelope.

Purpose: Mobile "nearby stops" without client-side bounding-box math.
Output: 2 new pure helpers, extended get_stops, 6 new tests + a test-only destination_point helper, docs/api.md update.

CLAUDE.md order: Task 1 spec, Task 2 RED tests, Task 3 GREEN implementation.
</objective>
